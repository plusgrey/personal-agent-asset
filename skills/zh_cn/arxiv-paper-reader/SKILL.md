# arXiv Paper Reader

目标：让读者**读完笔记就能复述这篇论文的逻辑链，并能独立重推其中的关键公式**。
这不是摘要，而是一份"把论文讲明白"的讲义。

## 工作流程

### 1. 获取论文

用户可能给出 arXiv ID（`2006.11239`）、abs/pdf 链接，或本地 PDF。

对于 arXiv 论文，运行（`<skill_dir>` 指本 SKILL.md 所在目录）：

```bash
python3 -I <skill_dir>/scripts/fetch_arxiv.py <id-or-url> --out ./arxiv-papers/<id>
```

脚本会生成：
- `meta.json`：标题、作者、摘要、分类、日期
- `main.tex`：**优先读这个**。这是 LaTeX 源码，`\input` 的内容已合并进来，公式最准确
- `source/`：完整源码，附录可能在单独的 `.tex` 文件里，图在这里
- `paper.txt` / `paper.pdf`：没有 LaTeX 源码时的后备。从 PDF 提取的公式可能不准，引用前要对照 PDF 核实

如果脚本无法联网，就让用户提供 PDF，或者用其他可用的抓取工具。

### 2. 通读，建立逻辑骨架

先完整读一遍正文和附录，再动笔。读的时候回答这几个问题：

1. **问题**：这篇论文要解决什么问题？为什么这个问题重要？
2. **现状**：现有方法是怎么做的？它们的**具体**缺陷是什么？要落到可验证的点上，比如"采样需要 1000 步"，而不是"效率低"
3. **洞察**：作者的切入点是什么？他们看到了什么别人没看到的东西？这是全文的核心
4. **方法**：洞察怎么变成具体的方法？每个设计选择对应解决哪个缺陷？
5. **证据**：实验能不能真正支撑论文的主张？有没有消融实验？比较的基线是否公平？
6. **边界**：方法在什么条件下会失效？作者自己承认了哪些局限？
7. **具体例子**：选一个足够小、但能覆盖核心机制的输入，逐步展示它在方法中如何流动。例子必须写出中间状态，不能只做类比。

### 3. 设计一个贯穿示例（必做）

每篇笔记都必须包含至少一个具体、可追踪的例子。先用一句话说明例子要解释论文的哪个核心机制，再逐步展开输入、中间状态和输出。优先使用贯穿全文的同一个例子，避免每节换一套设定。

按论文类型选择合适形式：

- **LLM / 深度学习论文**：从一个带形状的张量开始，例如 $X\in\mathbb R^{B\times L\times C}$，给出一组小尺寸（如 $B=2,L=4,C=8$）；逐层写清 reshape、投影、attention、mask、聚合或路由后形状如何变化。除了 shape，还要解释其中一个 token/向量的信息从哪里来、流向哪里。不要只罗列维度。
- **Agent 论文**：给出一个具体用户任务，展示 system prompt、用户输入、工具说明、memory/retrieval 如何组成 prompt context；画清楚 observe → reason/plan → act/tool call → tool result → update state → stop 的 loop，说明使用的 harness/runtime、可调用工具、状态保存位置、终止条件和错误恢复。论文未披露的实现细节必须标成“论文未说明”，不能猜测。
- **数学 / 理论论文**：先选最简单的标量或低维函数，用具体数字手算一遍；再推广到向量、随机变量或论文的一般形式。例子要由浅入深，并指出简单例子保留了什么机制、忽略了什么条件。
- **系统 / 数据库 / 编译器论文**：给出一个最小请求、查询、程序或数据块，沿真实处理流水线跟踪队列、缓存、调度、通信和状态变化；能量化时写出延迟、内存或复杂度。
- **其他类型**：选择一个读者可以手工验证的最小输入，逐步追踪核心算法，而不是重复论文中的抽象描述。

如果一个例子不足以解释方法和数学，可增加第二个例子，但仍应保持最小。例子中的数字、张量形状或 prompt 内容若由你自行构造，要明确标注“教学示例”，避免让读者误以为来自论文实验。

### 4. 数学推导（论文涉及公式时必做）

严格按照 [references/math-derivation.md](references/math-derivation.md) 的规范来写。要点：

- **每一步只做一件事**，并在旁边写明依据，比如"由 Bayes 公式"、"由 Jensen 不等式"、"对 $\theta$ 无关项丢弃"
- **论文跳过的步骤要补全**。"易得"、"经过简单计算"之类的地方往往最需要展开
- **遇到二级结论**（推导中当工具用的引理、不等式、恒等式），在第一次用到时插入一个"二级结论"块，写清楚：陈述、直观含义、简短证明或证明思路、在本文中具体怎么用
- 补全的步骤和论文原文要区分开。论文里有符号错误或省略了假设的地方，要明确指出来

### 5. 写笔记

按照 [references/output-template.md](references/output-template.md) 的结构输出 Markdown 文件。
默认保存为 `./arxiv-papers/<id>/notes.md`；用户另有指定的，按用户的来。

写作要求：
- 默认用中文写。术语第一次出现时附上英文原文，比如"证据下界（ELBO）"
- 每个部分先给结论，再展开论证
- 用自己的话讲清楚，不要大段翻译原文。只有关键定义才引用原文
- 数字结果要注明出处（表/图编号）和比较条件，不能凭印象写
- 区分**论文的主张**和**你的判断**。启发和批评部分可以有观点，但要说明理由
- 公式用 `$...$` / `$$...$$`，保证在 GitHub、Obsidian、Typora 里都能渲染

### 6. 自检

交付前过一遍：
- [ ] 动机 → 缺陷 → 洞察 → 方法 → 效果，这条线是否连贯，每一环都能接上上一环？
- [ ] 每个关键公式是否都从定义一步步推到了结论？每一步是否都写了依据？
- [ ] 用到的二级结论是否都介绍过了？
- [ ] 实验数字是否和原文一致？
- [ ] 是否包含至少一个从具体输入走到输出的贯穿示例，并展示了关键中间状态？
- [ ] LLM 例子是否写清张量 shape 和信息流？Agent 例子是否写清 context、loop、harness 与终止条件？数学例子是否从简单数值推广到一般形式？
- [ ] 自行构造的例子是否明确标为“教学示例”，未把推测伪装成论文事实？
- [ ] "对开源项目的启发"是否具体到可以落地，而不是泛泛而谈？

最后告诉用户笔记保存在哪里，并用三五句话概括论文的核心逻辑。
